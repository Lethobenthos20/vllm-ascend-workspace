# 产品目标与实际入口的一致性审查

本次依据用户纠正：产品目标没有“只读 / 稍后”档位。正常路径是显式使用、补齐必要目标和范围、自动采集整理贡献、后续可选复用。既有代码、文档和绿色测试不能反过来证明产品目标。

## 已定位的共同根因

1. 三端把 read-only/later 记录成完成初始化；Stop 按该配置正确跳过了核心业务。此前原生验收选择了这个分支，因此没有覆盖核心闭环。
2. 状态混用了安装完成、偏好已保存、任务绑定与实际采集可用。Codex 还可能同时返回 enabled 设置和拒绝贡献的保存值。
3. 配置写入和“选择完成”的顺序不一致。Codex/Kimi 的配置失败可能先留下 contribute，使下一次入口错误地认为配置已完成。
4. 首次绑定时贡献未配置，随后配置成功后，Codex 没有为同一任务完成采集绑定；必须再次激活才接上。用户不应编排这一步。
5. 普通状态提示把批次核对等内部维护交给业务 Agent；另有“故障暂停后重新激活”的陈旧文本，与共享运行时的持久绑定契约冲突。
6. Codex 整理器通过 `--ignore-user-config` 隔离工具时也丢失了已配置的模型与思考强度。业务任务使用指定模型不能证明后台模型一致。修复只传递配置中的模型标量，保持工具隔离；独立整理进程的只读沙箱不等于禁用产品采集贡献的只读模式。
7. Windows 原生 Codex 0.158.0-alpha.2.1 的 marketplace 清单只返回名称与路径，升级器却要求可选的 `sourceType`。固定夹具总提供这个字段，掩盖了自己的安装无法升级。修复接受明确归属于本升级器的目录，仍拒绝来源不明的外部目录，并在停服务前校验。

Grok 独立审查识别了前两类模式偏差及批次提示问题，未执行测试。审查提示误将 CC 的 535b630 称作历史夹具；本次另查 upstream main 后确认它是当前 CC 主线，按当前实现修正。历史验收报告保持原样，不能改写成新的覆盖证据。

## 修复边界

- 新入口不再提供、解析或记录 read-only/later 产品模式；旧保存值继续按原拒绝意图读取，不自动变成公开贡献。
- 缺配置、明确停用、损坏、范围不匹配、组件失败分别呈现；保存过选择不能掩盖缺配置。
- 配置成功后才记录完成；当前已绑定任务自动准备采集，保留原任务身份和时间边界。
- 普通状态不要求业务 Agent 执行批次恢复；共享 worker 保持既有自动恢复职责。明确操作人员仍可使用诊断工具。
- 独立故障上报、原生身份和信任、范围及明确停用边界保留。不新增工作流、报告表单或重试框架。

## 测试为什么没有拦住

原有用例常以实现中的选择枚举、响应形状和退出码作为正确性标准。它们验证了“选了只读后确实不采集”，却没有验证“完成配置后应自动采集”。此前几百个组件用例和只读原生验收都不能推出真实业务闭环成功。

新增测试按独立故障轴验证真实配置、保存状态和任务绑定路径：缺目标、已保存但缺配置、旧拒绝值、范围外任务、服务失败、配置失败后重试、配置完成后同任务采集准备。只在外部服务接点注入故障，不把整个产品过程 mock 成成功。模型调用与真实发布证据单列；组件通过不自动解锁完整验收结论。

CI 先跑短的产品结果检查，再跑协议、归属和平台组件套件。原生 Codex 在 Windows PowerShell 与 WSL 的安装、实际 Stop 送达、采集入库、整理产物、公开贡献回执及新任务检索仍须逐项记录。Kimi 模型验收依用户要求暂缓。没有真实回执的步骤保持未验收。

真实 NPU 验收已在现有 Ascend 容器中运行 Qwen3-0.6B。两端首次脚本因在父进程提前初始化 NPU 后使用 fork 而失败，修正后生成成功。失败属于验收脚本的启动顺序，保留失败与成功两份证据，不能归咎为适配器故障，也不能用最终退出码抹去过程。真实模型、设备占用与发布凭据属于受控原生验收条件；普通托管 CI 没有这些条件，组件绿灯不表示这些步骤完成。

Grok 将 CC 的候选身份测试从每次联网克隆并重装整套依赖，改为显式提供精确提交、复用已验证的官方依赖，再执行真实 `git+file` 安装并读取 pip 生成的来源元数据。缺输入、错提交、缺运行时均在安装前失败。修改没有删除错提交拒绝检查，也没有写入伪造来源；完整套件与该受影响测试的计时分别记录，不将两者直接作为加速比。
