# Codex 公开对话链路重写与验收

本轮按用户确认的方案处理 Codex：程序筛选和脱敏原生对话，直接保存正文；
模型仅可生成标题和检索摘要。Kimi 模型验收暂缓，Grok 不作为待适配客户端。
Grok 4.7/xhigh 参与了测试框架反例审查，但它未完成最终审查报告；不能将其记为审核通过。

## 固定的产品行为

1. 保留用户输入、助手公开进度说明和最终回答，保留顺序和文字。
   不读工具结果、隐藏推理、系统/开发者提示、注入的目录或继承的父任务历史。
   附件只留下类型占位，不读取文件或远端 URL。
2. 本地使用固定 SHA256 的 Gitleaks 8.30.1 和既有隐私规则脱敏。
   安装时准备组件；运行时不下载、不调用模型。忽略外部 Gitleaks 配置和允许泄漏注释。
   原始材料只保留在宿主 transcript；新的 Stop 队列不再复制未脱敏的最终回答。
3. 贡献授权首次确认后长期保存，后续任务、重启和升级自动复用，不按任务或时间失效。
   每个原生任务保存一条可追加记录；只有用户主动关闭、重新开启或调整授权范围时，才改变内部授权版本。
   继续对话、重复 Stop、进程重启、
   发布后的续写使用原有身份、游标和回执，不新造重试或任务系统。
4. 正文先保存，随后可查询和贡献。默认标题/简介明确采用正文摘录，续写后更新摘录。
   可选模型只能返回标题和摘要。适配器内部固定 GPT-6-Luna / low，安装与升级自动配置，不让用户选择；失败、超时或不支持均不影响正文。
   摘要使用已脱敏的完整正文；独立执行，不阻塞新正文。
5. 授权撤销、损坏记录、无法确认时间边界或脱敏组件失败都留下可查状态。
   旧模型流程的失败区间和待应用结果保留诊断，不能在新路径中重放或偷偷重新调用正文模型。

正文没有按字数调用模型，也不再使用“把 140 秒改成 300 秒”处理增长的输入。
公开消息按完整记录读取，不截掉大消息尾部。平台文件限制、无效输入和权限边界仍须如实报告。

## 为什么过去用例多却拦不住

旧测试验证了许多内部返回值，却没有把“产品可用”固定成共同结果：
入口成功可能只表示绑定或检索可用；模型替身总返回理想内容；旧格式解析器、
单一虚拟环境和 shell 不能证明真实 Codex 输出、Windows 子进程和公开贡献都能工作。
部分早期用例在同一 CI 中又被全量发现重复运行，增加成本但不增加边界覆盖。

现在适配器的 `tests/run_ci.py` 每例只运行一次，先验证安装/依赖合同、产品状态、
进程生命周期、shell 入口和公开正文；失败立即停止。核心和适配器使用同一精确固定依赖。
“只读 / 稍后”不再是配置完成的产品模式；明确关闭贡献仍被尊重并显示为关闭，不能算完整链路通过。

| 独立边界 | 实际检查结果 |
| --- | --- |
| 原生格式 → 公开文本 | 两种 Codex 文本形态、注入内容、缺失时间、fork、重复包装和大消息；不以递归搜索所有 text 字段代替格式适配 |
| 公开文本 → 脱敏正文 | 真实 Gitleaks 密钥正例，以及公开版本号、哈希、shape、dtype 的反例；Windows/WSL/URI 路径别名与 Unicode |
| 正文 → 本地记录 | 无模型也能入库；事务失败不推进游标；重复 Stop、重启、追加和撤销分别验证 |
| 可选摘要 → 检索信息 | 禁止返回正文字段，禁止继承业务 max 思考强度，旧版本结果不能覆盖新正文，失败保持正文可用 |
| 生命周期 → 后台服务 | 真实短进程退出、冷 Stop、Windows Job 所有权、独立 Python 和虚拟环境；失败留下诊断 |
| 导出 → 公开仓库 | 组件用例比较实际导出字节；实机验收另查自动 PR、远端 commit、脱敏正文与精确回执 |
| 公共知识 → 使用 | 正式 feed 同步之后，以新的原生会话检索并读取正文；不把旧 feed、相邻条目或本地草稿算作命中 |

真实业务还暴露了本地续写标题停留在启用说明、后台 wake 第二次脱离 Windows Job 被拒绝，
以及冷 PowerShell 启动用完宿主 2 秒窗口。这些均已修复。公开仓库经维护者修改的标题仍由远端决定，
不能把本地摘录更新误称为强制重写远端标题。
Stop 宿主上限现在为 5 秒，包含 shell/解释器冷启动；实际交接预算仍为 Windows 1.3 秒、
其他平台 1.5 秒，Hook 不解析 transcript，不随正文大小增长。

远端逐段对照还发现：首个 PR 合入后，查找自己已有 PR 的逻辑只认识初始分支名，
会忽略带后缀的续写 PR，从旧 main 新开 PR，并遗漏已经投递、尚未合入的内容。
现在按已有回执中的仓库、PR 编号和分支配对；多个未合入候选明确要求核查，不任意选基线。
回归通过真实 Git 走“首次合入、第二次续写、重启、第三次续写”，比较最终远端三个正文片段各一次。
旧实现确实错误打开第三个 PR；修正后复用第二个。测试用传输器也修复了更新 PR 后不移动真实
`refs/pull/N/head` 的失真，不能再只改模拟 API 结果。

检索自己的贡献在同步后曾把已发布版本标为 `draft`，现统一按返回版本标记 `feed`；
测试同时保留发布版本优先、尚未发布的本地追加另行标记的约定。
原生入口使用实际 Skill 清单中的 `$mindie-agent:mindie-agent`，避免裸名称未触发 Skill 的情况。
验收驱动不再把自身 UV Python 的 `PYTHONHOME/PYTHONPATH` 传入 Codex 子进程；这是驱动环境隔离，
并未更改用户全局 Python 配置。此前失败均保留，不计为最终新会话成功。
Windows 的首次入口直接给出 `python` 命令，macOS/Linux 给出 `python3`，
避免模型照抄统一示例后撞上 Windows 的 Microsoft Store 别名。

## 后续检查如何控制成本

- 每个代码 PR 使用固定依赖和边界测试，不调用模型或占 NPU。断言最终可见正文、实际锁/进程、
  远端 Git 文件和回执，避免模型替身返回成功就算业务成功。
- 原生 Codex 版本、安装器、Skill 入口或 Hook 改动时，在 Windows/WSL 各做一次真实原生回合，
  验证绑定、自动 Stop、无模型正文及新会话读取。操作系统定时器另测，不能从 worker 存活推断。
- 发布、恢复、撤销等状态边界先用真实本地 Git/SQLite 做独立场景；真实 GitHub 验收再核对
  精确公开文件与回执。采集成功、打开 PR、Bot 合入、同步、读回是不同结果，不能互相替代。
- NPU 执行只在设备/远端路径或业务执行行为变化时重跑；纯检索标识和 Skill 文案变更复用
  已核实的设备日志。可选摘要模型按单独通道验收，不把 provider 故障混进正文或 NPU 测试。

上述分工减少重复用例和无关设备运行，并不以用例数量承诺不存在缺陷。

## 验收边界

- 上述 `8ecdd56` 验收时，worker 强制要求 `none`，账号拒绝已探测的 GPT-5.4，
  GPT-6 未提供 `none`，因此当时使用正文摘录。后续用户确认可直接使用 GPT-6-Luna，
  当时修订移除了这项强制要求；后续产品契约改为内部固定 Luna/low。早期验收不改写为模型摘要成功。
- 隔离 profile 的自动升级设为 manual，避免未合入候选被 main 覆盖。
  知识同步使用正式更新器的知识同步入口单独执行；此项不宣称 OS 定时器自动投递通过。
  自动 Stop、后台入库和知识 PR 由原生回合及既有服务完成，没有手工补发 Stop 或改游标。
- 旧模型路径的 WSL 失败区间仍保留，新的成功任务不抹掉历史失败。
- 规则脱敏不能判断商业机密语义，也不能保证识别拆散在不同消息中的任意秘密。
  已确认的项目范围仍是贡献边界，公开仓库 Bot 不能补救上传前漏脱敏。
- Kimi/Claude/Grok 的原生模型验收不在本次 Codex 通过结论内。
