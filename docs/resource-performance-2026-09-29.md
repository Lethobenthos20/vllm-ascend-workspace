# 本机资源开销检查：PowerShell 与 WSL

本轮范围是 MindIE Agent 的本地控制面：三个 Harness 适配器、共享知识核心、remote-dev、本地诊断、安装与旧 VAWS 退役。业务正文不截断，公开对话保留用户输入、公开说明和最终回答；不采集隐藏推理，也不把工具输出送进正文。性能修改沿用现有贡献授权与发布契约。

## 怎样测

同一台 Windows 主机，分别用 PowerShell/NTFS 与 Ubuntu-24.04 WSL/ext4，Python 3.13.12。使用冻结的修改前源代码和实际候选源代码；每个场景启动独立进程、独立状态目录，三轮交替前后版本，串行运行。输入都是合成公开文本，无远端发布、无模型调用。

记录耗时、进程 CPU 时间、RSS 采样峰值、逻辑读写量和状态文件大小。RSS 每 20 ms 采样；父进程每 50 ms 另外采样进程树，因此子进程 CPU 是可能漏掉短进程的下界，进程树内存包括准备输入阶段。它们不能冒充精确的总 CPU 或瞬时峰值。Windows CPU 时钟有量化误差，极短场景出现 0 不代表没有 CPU 开销。磁盘表中的读写是包含缓存和管道的逻辑 I/O，不是物理硬盘写入量。历史队列场景额外记录 SQLite 每 1000 条虚拟机指令的进度计数。

Linux 的 `/proc/pid/io` 会计入已经等待结束的子进程，Windows 的进程 I/O 不会；因此读写量只在同一系统内前后比较，不能再把 Linux 子进程采样值加进去，也不能直接比较 Windows 与 WSL 的绝对值。参见 [Linux proc_pid_io 手册](https://man7.org/linux/man-pages/man5/proc_pid_io.5.html)。

目录大小统计发生在 I/O 起点之后、CPU 起点之前，因此逻辑 I/O 中含这次目录遍历；RSS 采样线程的少量 CPU 也包含在测量内。进程树 RSS 是各进程 RSS 相加，可能重复计算共享页，不能当作独占物理内存。

三轮的中位数、最小值和最大值在 [JSON 数据](resource-performance-2026-09-29.json)。复现入口：

```sh
python tools/resource_audit.py --source-root /path/to/sibling-repositories --work-root /new/evidence/directory
```

测量依赖 `psutil==7.2.2` 和各适配器锁定的完整 runtime。源代码目录包含 `knowledge`、`audit-diagnostics`、`audit-remote-dev`、`mindie-agent-codex`、`mindie-agent-kimi`、`mindie-agent-cc`。需要额外定位热点时加 `--profile`；带 profiler 的数字不参与最终前后对比。脱敏场景使用真实 Gitleaks，缓存安装步骤在计时区间外。

## 覆盖范围

| 部件 | 实测场景 | 检查重点 |
|---|---|---|
| 共享核心 | 新解释器导入、约 1.5 MiB 文本分词与标题摘录、200 条知识的 100 次查询 | 全文临时对象、重复分词、搜索结果保持 |
| 后台工作 | 空库与 40 条约 256 KiB 待贡献正文各空闲 6 秒；三张表各 5 万条历史记录的 100 次检查 | 空闲正文读取、历史数据越多越慢、后台写盘 |
| 对话链路 | Codex、Kimi、Claude Code 各 24 次真实解析、脱敏、追加；最终正文约 0.87 MiB | 正文无丢失、每个标记恰好一次、游标完整、单任务单记录 |
| 原生 Hook | 三个适配器各 10 次未配置 Stop 入口；Codex 在 Windows 经过实际 PowerShell 壳 | 冷启动时间、安静返回、未配置时不写状态 |
| 诊断 | 6000 条真实事件；1000 条事件首次摄取及其后 9 次空闲摄取 | 每条日志系统调用、轮转、读取游标、重复读取 |
| remote-dev | 10 个真正的受管理本地进程、双向管道、持久化回执 | Windows 进程树管理、额外扫描、取消回收 |

这不是远端 SSH、NPU 算子或模型吞吐测试。模型生成摘要、网络发布、首次下载、操作系统文件缓存和原生 Harness 自身内存，不混进本地核心的改善数字。已有环境重用和安装体积单独检查。

## 修复

1. 空闲检查只读待处理元数据，不再取出所有草稿正文；队列先筛选可重试时间再限制数量，避免两个延后的条目挡住后面的可执行条目。取消未发送条目使用一次数据库更新，保留结果不确定的回执。
2. 给采集状态、待生成摘要、待应用结果、活动发件箱增加索引。历史记录仍保留，轮询不再扫描全部已完成工作。
3. 重复标识符复用分词结果，索引文本分块拼接；正文不受缓存大小限制。标题与摘录取得所需前缀后结束处理，不再拆解整段对话。
4. SQLite 继续保存正文和固定版本引用，移除没有产品读者的 Markdown 草稿镜像写入。发布时从选定版本生成文件，重启、旧引用与公开导出均有回归检查。
5. 日志每条只检查压力标记是否变化，变化时重新验证；打开或轮换日志文件前仍完整验证。现有文件描述符之间的写入不再逐级检查目录。
6. Windows 子进程分配 Job 后直接恢复持有的进程句柄，不再遍历整机线程。原生 API 的错误码单独转换，失败仍清理子进程，隐藏窗口和子孙进程所有权保持。这条调用与 [psutil 的 Windows 实现](https://github.com/giampaolo/psutil/blob/master/psutil/arch/windows/proc.c)一致；没有引入新运行依赖。五份启动实现由测量入口检查同一函数内容，避免只修一个客户端。

## 结果

以下均为三轮中位数，箭头表示修改前 → 修改后。CPU 是执行场景的 Python 进程累计 CPU 时间，不包括子进程 CPU；不是任务耗时，也不是整机占用率。

| 场景 | Windows CPU（秒） | WSL CPU（秒） | 主要变化 |
|---|---:|---:|---|
| 文本分词 | 0.156 → 0.078 | 0.119 → 0.056 | 峰值 RSS：48.4 → 31.1 MiB / 46.0 → 32.0 MiB |
| 6000 条诊断日志 | 1.422 → 0.500 | 0.545 → 0.353 | CPU 分别减少约 65% / 35%；日志量不变 |
| 40 条大正文待处理时空闲 6 秒 | 0.125 → 0.047 | 0.132 → 0.072 | 状态文件：36.7 → 26.7 MiB；不再重复读取正文 |
| 历史队列 100 次检查 | 0.750 → 低于时钟分辨率 | 0.439 → 0.001 | 耗时：0.741 → 0.002 秒 / 0.427 → 0.001 秒 |
| 10 个受管理本地进程 | 0.734 → 0.047 | 0.014 → 0.015 | Windows 耗时 1.255 → 0.553 秒；POSIX 启动实现未变 |
| Codex 24 次增量采集 | 2.578 → 1.938 | 1.812 → 1.276 | 总耗时 9.542 → 8.775 秒 / 7.850 → 7.250 秒 |

三个客户端的完整采集结果：

| 客户端 | Windows / WSL 峰值 RSS（MiB） | Windows / WSL 逻辑写入（MiB） |
|---|---|---|
| Codex | 62.1 → 56.5 / 64.7 → 58.4 | 59.14 → 48.46 / 59.13 → 48.45 |
| Kimi | 62.5 → 55.9 / 64.1 → 56.7 | 59.14 → 48.46 / 59.14 → 48.46 |
| Claude Code | 62.7 → 54.5 / 65.8 → 58.1 | 59.14 → 48.47 / 59.14 → 48.46 |

减少约 18% 的逻辑写入来自取消重复草稿镜像；完整脱敏仍执行，完整正文、固定版本和游标检查全部通过。仅优化 Python 整理部分不会等比例缩短 Gitleaks 等子进程占据的总耗时。

普通搜索、空库空闲、未配置 Hook 没有明显改善。Windows 空库 6 秒 CPU 为 0.016 → 0.031 秒，差一个计时粒度；不能宣称零消耗。WSL 本地进程场景耗时中位数为 0.128 → 0.144 秒，未改善。新解释器导入更快，但本轮没有清空操作系统文件缓存，不能称作物理磁盘冷启动测试。

新增索引使 15 万条完成历史记录的数据库从约 15.31 增至 17.39 MiB，空库增加约 52 KiB。这是明确的空间交换，不能宣称所有场景硬盘占用都下降。

索引会增加少量数据库存储，换取历史记录增长后稳定的轮询成本。正文历史仍占空间；为了固定版本引用和未确认发布的恢复，不删除这些材料。旧原生任务可能继续持有已安装代码，因此本轮不擅自删除仍可能被任务使用的 MindIE 代际缓存。

## 回归与发布

- Windows 核心完整检查：534 通过、30 项平台跳过；remote-dev：517 通过、105 项平台跳过；诊断：239 通过、12 项平台跳过。
- WSL 核心相关链路：147 通过；诊断：249 通过、2 项跳过；remote-dev 相关进程/连接池/SSH 契约：85 通过、1 项跳过。
- Windows 客户端：Codex 280 项运行通过（5 项跳过）、Kimi 246 项运行通过（6 项跳过）、Claude Code 159 项（8 项跳过）。Claude Code 首轮有 3 项因本地执行脚本漏传 CI 样本路径失败，按 CI 指定配置重跑该 3 项通过。
- 新增检查针对数据库实际查询工作量、正文读取次数、未来重试公平性、禁用后的不确定回执、固定旧版本、无镜像重启/导出、分词兼容、压力变化立即生效。避免把固定机器上的耗时作为单元测试门槛。
- 诊断 Windows 3.11 首次 push CI 出现一条日志未记录的偶发失败；同一提交的完整 PR CI 和失败 job 的单独重跑均通过，保留该失败记录，不以重跑证明问题不存在。
- 六个实现 PR 的当前 CI 均通过仓库声明的平台检查。独立 Grok CLI 使用 `grok-4.7`、`xhigh` 完成七个仓库的前后代码审查，未确认产品回归；审查只读，没有冒充执行测试。Linux I/O 归属、父进程 CPU、冷导入口径的问题已在工具和报告中修正，其余采样限制如上保留。标记缓存的目录替换假设未证明有路径逃逸：已打开的描述符继续指向旧文件，新段仍完整检查。该结论不等于形式化证明无缺陷。

## 默认安装验收

Windows 与 WSL 的默认 Codex 配置中，`mindie-agent@mindie-agent` 均已安装并启用。实际安装的 MCP 声明经过 `initialize` 和 `tools/list`：知识服务返回 3 个工具，remote-dev 返回 11 个工具，关闭输入后服务正常退出。

| 实际安装的服务 | Windows 进程树 RSS | WSL 进程树 RSS | Windows / WSL 工具发现时间 |
|---|---:|---:|---:|
| 知识 | 34.2 MiB | 22.0 MiB | 0.158 / 0.033 秒 |
| remote-dev | 31.3 MiB | 19.0 MiB | 0.131 / 0.023 秒 |

每个服务分别观察 3 秒空闲，进程树 CPU 时间均未测到增长。这是短时观测，不等于任何状态都零开销；Windows 的 Python 启动包装进程也计入上表。安装目录普通文件的逻辑总大小约 Windows 6.18 MiB、WSL 6.54 MiB，不含共享 Python、uv/Gitleaks 下载缓存、Codex 自身缓存和符号链接目标，也不是物理占盘量。Windows 生成配置统一使用实际 MSIX 存储路径，避免依赖应用内路径映射；大小含此次安装重打包保留的上一代。

沿用用户已批准的贡献仓库、账号和隔离验收目录，未扩大贡献范围；诊断上传保持原来的禁用选择，其他原生插件保留。依赖 PR 尚未合入主线，本机暂固定该候选版本并使用手动更新，避免自动切回旧主线。新建任务才会加载更新后的定义；变更的 Hook 信任仍由原生客户端处理。本轮没有将 MCP 连接检查冒充模型任务或真实 NPU 验收。

## 本机旧 VAWS 退役

Windows 旧 VAWS MCP 入口、自动 Skill 入口、3 个计划任务、对应进程树和全局运行环境已移除；额外清除工作区中的 Windows、Linux、reference-intake 三个旧虚拟环境。WSL 的旧 systemd 服务、旧安装环境、旧状态及验收缓存已停止或移除。旧配置和必要历史资料保存在本地备份，不加入版本库。

业务 `vllm`、`vllm-ascend` 仓库、历史任务和用户未提交内容保留。约 228 万个旧运行文件大量使用硬链接，不能把它们的逻辑大小宣称成同样多的可用空间；Windows 全局目录删除期间观测到的 C 盘净空闲变化约 66 MiB，也包含其他同期写入。
